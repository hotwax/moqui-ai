# Return synchronization lifecycle

## Purpose

Return synchronization moves an OMS return through the NetSuite documents required to represent its inventory and financial outcome. A return is not complete in NetSuite merely because one document exists. The required documents depend on the return source, inventory disposition, and refund method.

## Systems and ownership

- Shopify owns customer-facing order, return, refund, and exchange activity for Shopify returns.
- AfterShip owns the customer-facing workflow for AfterShip returns and warranties.
- OMS links the source events, returned products, receipts, replacement orders, and refund payment preferences.
- NetSuite owns the accounting documents and NetSuite inventory receipt.
- NetSuite return history in OMS records the NetSuite IDs already created for the return.
- Stored AfterShip SystemMessages prove which warranty webhooks reached OMS and whether each message was consumed successfully.

## Main lifecycle

1. A source return is created or updated in OMS.
2. OMS determines whether an RMA is required.
3. Inventory receipt is either created by OMS in NetSuite or created in NetSuite and synchronized back to OMS.
4. OMS waits for a completed return and a resolved refund outcome before financial settlement when those prerequisites are required.
5. OMS creates the Credit Memo and, depending on the outcome, a Customer Refund or invoice/application transaction.
6. History becomes `SYNCED` only when every document expected for that scenario is present.

## Meaning of return states

- `RETURN_REQUESTED` means the return exists, but physical receipt or customer resolution may still be pending.
- `RETURN_COMPLETED` means the source return workflow has completed. It does not prove that every NetSuite document exists.
- `RETURN_CANCELLED` and `RETURN_REJECTED` are not actionable through normal return synchronization.
- A no-proof-of-purchase warranty with an active `NO_POP_WARRANTY_HOLD` is intentionally waiting and must not be retried as a technical failure.

## Meaning of NetSuite history states

- No history means no NetSuite return document has been recorded by this flow.
- `PARTIAL` means at least one NetSuite artifact exists, but another expected artifact is still pending.
- `SYNCED` means all artifacts expected by the current scenario should exist.
- A `SYNCED` history with a missing expected RMA, Item Receipt, Credit Memo, Customer Refund, or invoice is inconsistent and must be investigated.

## Document roles

- Return Authorization, or RMA, represents authorization of returned merchandise.
- Item Receipt, or IR, records inventory received against the RMA.
- Credit Memo, or CM, records the credit generated by returned merchandise.
- Customer Refund, or CR, sends money back to an original payment method when required.
- Invoice is used by the configured store-credit or exchange application flow when that outcome requires it.

## Historical orders

The original order may predate OMS. If OMS has the Shopify order identifier but no local NetSuite order identifier, the synchronization can look up the Sales Order in NetSuite. Absence of a local `NETSUITE_ORDER_ID` does not by itself mean that an RMA cannot be created.

## Diagnostic principle

Always explain the return in this order: source state, OMS linkage, expected NetSuite documents, documents actually recorded, current eligibility, blocking prerequisite, and next action. Do not call an intentional wait an error.
